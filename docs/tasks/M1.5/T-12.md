# T-12: M1.5 parity gate

## Objective
The parity gate is run and recorded: feature-parity.md is re-run on Linux, macOS
and Windows, performance.md budgets are measured on all three OSes, and the owner
signs off. **This task is a gate, not a feature.** Its outcome decides whether
T-14 may start.

## Context
Source: implementation-roadmap.md §1 (wave E), §2 (T-12 acceptance), §5 and
exit criteria 1–6 of M1.5. Documents: `docs/migration/qt-to-tauri/feature-parity.md`,
`performance.md` (§2 targets), `decision.md` (owner sign-off record). Verification
record: `docs/roadmap/verification/M1.5.md` (T-10).

## Required interfaces
- `docs/migration/qt-to-tauri/feature-parity.md` (rows and statuses).
- `docs/migration/qt-to-tauri/performance.md` §2 (budget table).
- `docs/migration/qt-to-tauri/decision.md` (sign-off record).
- `docs/roadmap/verification/M1.5.md` (T-10 output).

## Implementation requirements
1. Gate condition A (feature parity): every row of feature-parity.md is ✅, or is
   explicitly waived by the owner with the waiver recorded in decision.md.
2. Gate condition B (performance): the budget table in performance.md is filled
   for Linux, macOS and Windows (CI runners) plus one manual run per OS on real
   hardware with a GPU (roadmap exit criterion 3). Any budget missed is listed,
   not waived silently.
3. Gate condition C (M1 criteria): all nine M1 exit criteria pass on the Tauri
   shell on the three OSes in CI (exit criterion 1).
4. Gate condition D (CI): `scripts/check.sh` runs the Tauri gates; CI is green on
   all three OSes, or red cells have a recorded owner (exit criterion 4).
5. Gate condition E (manual): T-10 verification recorded in `M1.5.md`, with no
   open blocker (exit criterion 5).
6. Gate condition F (packages): T-13 artifacts install, launch and connect (exit
   criterion 6).
7. The owner's sign-off is recorded in `decision.md` with date and the list of
   waivers; without it the gate is not passed.
8. Record the gate outcome in `docs/roadmap/current.md` as "passed" or "not passed",
   with the failing conditions.

## Constraints
- Documentation only in this task: no code change. If a gate condition fails,
  the fix belongs to the task that owns the scope (reopen it or raise a CR under
  governance); T-12 does not implement it.
- No row is changed to ✅ without evidence named in the row.
- Daemon and protocol 0.1 unchanged.

## Acceptance criteria
1. Gate conditions A–F each recorded as met or not met with evidence (req. 1–6).
2. Owner sign-off recorded in decision.md with waivers listed (req. 7).
3. `docs/roadmap/current.md` states the gate outcome (req. 8).
4. T-14 and T-15 are not started unless this gate is "passed" (see T-14, T-15 gating).

## Tests
- `scripts/check.sh` — green on the commit being gated (all three OSes in CI).
- `python3 scripts/tasks.py check` — board consistent.
- Performance: `apps/desktop-tauri/bench/run.sh` per OS; results in `bench/results/`
  cited by name.
- Feature parity: the gate reviewer re-runs the evidence named in each row.

## Failure conditions
- Any gate condition A–F is not met and the gate is recorded as passed.
- A performance budget is missed and not listed.
- Any OS is missing from the evidence and the gate is recorded as passed.
- The owner sign-off is absent or inferred.
- Rows marked ✅ lack a named test or run.

## Documentation updates
- `docs/migration/qt-to-tauri/feature-parity.md` — final statuses.
- `docs/migration/qt-to-tauri/performance.md` — budget table per OS.
- `docs/migration/qt-to-tauri/decision.md` — sign-off record.
- `docs/roadmap/verification/` — M1.5 gate result (`M1.5.md`).
- `docs/roadmap/current.md`.

## Handoff
The gate result (passed / not passed) with conditions A–F each marked, the list
of waivers, the owner's name and date, and the commit hash gated.
