recorded below and neither hidden: the Windows end-to-end run (KD-WIN-2, new)
and the Windows Qt job (KD-WIN-1, carried over from M1). T-14 (make Tauri the
default) and T-15 (delete Qt) were therefore **not** executed. See §7.

## 4b. Cross-target compilation

The shell has three platform-specific code paths (macOS menu, Linux crash hook,
Windows/macOS process lookup). This machine can only *run* the Linux one, but
both other targets can at least be **type-checked**, which is how the macOS
menu stopped being code nobody had ever compiled:

| Target | Result on this host |
|--------|---------------------|
| `x86_64-pc-windows-msvc` | **`cargo check --all-targets` passes** (whole graph + our code), once `llvm-rc` is on PATH — `tauri-winres` needs it to emit the resource file. `llvm-rc` came from the Fedora `llvm` RPM, extracted without root the same way `scripts/sysroot.sh` handles WebKitGTK. |
| `x86_64-apple-darwin` | **`cargo check --all-targets` passes**, with `CC/CXX_x86_64_apple_darwin=clang`: the one C build script in the macOS graph (`objc2-exception-helper`) compiles on Linux clang. |

Both are reproducible: `apps/desktop-tauri/scripts/cross-check.sh` adds the Rust
targets, creates the placeholder sidecars `externalBin` requires, and runs both
checks (it fails, rather than silently passing, when `llvm-rc` is missing).

**Proof the macOS path is really compiled**, not skipped: a deliberate type
error inserted inside `install_menu` (the macOS application menu, T-07) makes
the macOS check fail with `E0308 expected u8, found &str`; the error is absent
for the Linux target. So the menu's Tauri-API usage is compile-verified against
the real crate, on its real target.

**What this does not prove:** nothing is linked, launched, packaged or tested on
macOS or Windows. A type-check cannot show that the menu appears, that
WebView2 hosts the page, or that the Windows end-to-end path works. Execution
evidence still requires CI (T-09) and one real machine per OS (T-10).

What *was* made verifiable instead: everything platform-specific that is
JavaScript — the per-OS process lookup used by the crash test — was extracted
to `e2e/processes.mjs` and is unit-tested for all three platforms (10 tests),
including the `ps` 15-character `comm` truncation that broke the first
implementation.

## 5b. A pre-existing gap this work surfaced

The daemon's `task/start` **`shell` form** (`sh -c` / `cmd /C`) has never been
verified on Windows: M1's own note records `crates/exec` as "Linux only;
Windows compiles, untested". The CI run for M1.5 made it visible - two Tauri UI
tests drove commands through the shell and produced no output on Windows.

The M1.5 tests now use the **argv** form for what they actually assert (the
streaming and cancellation contract of the UI), and the gap is recorded here
rather than worked around: fixing `shell` on Windows is a daemon change and
belongs to its own task, not to the shell migration.

### KD-WIN-2 (new): the Windows end-to-end run cannot start a session

`tauri-driver` reaches msedgedriver (the Edge WebDriver downloaded to match the
runner's Edge), but the session fails with
`session not created: DevToolsActivePort file doesn't exist`. tauri-driver
passes `--port` and `TAURI_AUTOMATION=true` to the driver and expects the
WebView2 host to expose a DevTools endpoint; wry 0.57 does not act on
`TAURI_AUTOMATION`, so our app never opens one. Not diagnosed further: it needs
a Windows machine. Suspects, in order: the app must be built with a
Tauri-supported automation feature; or `webviewOptions` must be passed in the
session capabilities; or msedgedriver must be launched in webview mode with an
explicit binary. The step is left **red and named**, not silenced.

### KD-WIN-1 (carried over from M1): the Qt desktop job on Windows

Recorded in `verification/M1.md`: the Qt shell's Windows suite was never green
(two executables passed, the rest were not reached). Unrelated to the shell
migration; it disappears with T-15.

## 7. Why the gate did not pass, and what it needs

The M1.5 exit criteria (milestones.md) require:
1. the nine M1 criteria on **all three** OSes in CI → Linux only so far;
2. every parity row ✅ or waived → 5 rows need the owner's waiver (listed in
   `feature-parity.md`) or more tests;
3. the budgets on all three OSes → Linux only;
4. `scripts/check.sh` green → ✅ locally;
5. manual verification recorded per OS → Linux protocol written
   (`agents/MANUAL_VERIFICATION.md`), not executed;
6. packages for each OS install and connect → Linux only.

To finish the gate:
- push this branch and read the `tauri` CI job on ubuntu-latest, macos-latest
  and windows-latest (it runs build, Vitest, and the end-to-end on Linux and
  Windows);
- run the manual protocol on one real machine per OS;
- build the Windows/macOS packages in CI;
- owner review of the 5 open parity rows.

Until then `apps/desktop` remains the shipped shell (T-14/T-15 held).
