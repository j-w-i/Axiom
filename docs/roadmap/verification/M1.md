### Windows desktop: known defect (KD-WIN-1)

Progress in CI is real and reproducible; one class of failure remains, and it
is a *test-environment* problem, not an application one:

- `tst_linebuffer`, `tst_daemonclient` pass on Windows; `tst_workspace` failed
  on a path-separator comparison in the test itself (fixed: compare in native
  separators), and the remaining executables were not reached because ctest
  runs with `--stop-on-failure`.
- Two Windows-specific findings that were fixed in the product or CI:
  1. Qt for Windows loads its DLLs from `PATH`; another `Qt6Core.dll` earlier
     on `PATH` produced `0xC0000139` (entry point not found) at process start.
     Fixed by putting Qt's `bin` first (`GITHUB_PATH`) and deploying with
     `windeployqt` plus the newest VC runtime redist next to the binaries.
  2. Qt 6.12.0's Windows `qtwebengine` extension package was built months
     before the rest of 6.12.0 and fails to load the same way; the Windows CI
     entry therefore pins **Qt 6.11.3**, whose WebEngine and base packages were
     built the same day. (Linux and macOS use 6.12.0.)
- A real product bug found by Windows CI and fixed: `axiom-workspace`'s atomic
  replace could fail with access-denied on Windows when another process held
  the destination open; it now retries briefly before failing
  (`persist_with_retry`, Windows only).

Status at the time of writing: the Windows desktop job is not green. It is
**not** marked `continue-on-error` (no exception was taken); it is an open
defect with a concrete next step: run the remaining executables on Windows
after the path fix (`tst_documents`, `tst_tasks`, `tst_settings`,
`tst_smoke_launch`, `tst_smoke_editor`) and fix whatever they report, which is
the first thing M1.5 or M2's CI task must pick up if it is not done first.

The Linux desktop job was green in several runs; in one later run it was
cancelled inside `install-qt-action` while `apt-get` could not resolve
`archive.ubuntu.com` (≈10 minutes, runner-side DNS). That is infrastructure
flakiness, not a test result; the job has a 45-minute cap and the apt step for
extra runtime libraries is `continue-on-error` so a mirror problem cannot sink
it again.

## Unverified statements (explicit)

- No on-screen (real display) verification of any GUI behaviour was performed
  at the user's request; everything above is offscreen.
- IME, clipboard, drag and drop, HiDPI, a real GPU, screen readers and
  keyboard-only traversal of every control were not exercised.
- The native Open Folder dialog, the Open Recent submenu and menu shortcuts
  were not driven by real events (their handlers are the tested controller
  methods).
- macOS: Ctrl/Cmd+S delivered as a synthetic key chord does not reach Monaco;
  the smoke test falls back to the product's File ▸ Save path there and logs
  which path was used. Typing (plain key events) does reach Monaco on macOS.
- The renderer-crash test kills the real Chromium renderer process; on a
  platform where that process cannot be found it is skipped (QSKIP) and the
  restore path is covered at model level by
  `tst_documents::unsavedTextComesBackFromTheLatestSnapshotAfterACrash`.
- Windows: everything except `tst_linebuffer` and `tst_daemonclient` is
  unverified (see KD-WIN-1).
