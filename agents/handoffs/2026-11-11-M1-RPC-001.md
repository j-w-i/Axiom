## Behaviour implemented
- Codec: `\n` framing, `\r\n` accepted, empty lines ignored, lines > 64 MiB give `ServeError::LineTooLong`.
- Parse and invalid-request errors answer with `id: null`; connection stays up.
- `initialize` gate, version negotiation, `HostInfo`; second `initialize` is `invalid_request`.
- Per-request tasks; `$/cancel` with 100 ms grace and an unconditional `cancelled` response; panic → `internal`.
- `shutdown` / EOF run hooks (EOF cancels in-flight requests first); `after_response` futures run only after an Ok response is queued.
- Single writer task fed by a bounded channel.

## Deviations and decisions
- `Client::orphan_errors()` added (not in spec): receiver for `id: null` errors, needed to test behaviour 2.
- Unknown-id duplicate requests: a request reusing an id still in flight gets `invalid_request` (spec silent).
- Notifications other than `$/cancel` received by the server are ignored (no handlers for client notifications in 0.1).
- `$/cancel` processed = entry removed from the in-flight map; responses reserve queue space before checking the map, so the race rule is exact.
- `Cargo.lock` is tracked by git; it changed.
- The test of the 64 MiB limit streams 64 MiB through a duplex pipe (fast, ~0.4 s total).

## Known defects / limitations
- A cancelled request whose handler is aborted at 100 ms drops any `after_response` futures (by design).
