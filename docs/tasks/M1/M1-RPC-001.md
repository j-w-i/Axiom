# M1-RPC-001: Implement the `axiom-rpc` crate

## Objective
A domain-free library that serves the Axiom protocol over any async byte
stream: NDJSON codec, concurrent request dispatch to typed handlers,
`initialize` gate, `$/cancel`, `shutdown`, outgoing notifications with
backpressure, and a typed client used by tests (and later by the CLI).

## Context
Read: `docs/protocols/ipc.md` (all of it), `docs/architecture/modules.md`
§`crates/rpc`, `crates/protocol/src/{envelope,method,lifecycle,registry}.rs`.
Reference implementation of the idea (std-only, not to be copied verbatim):
`experiments/e1-qt-rust-monaco/daemon/src/main.rs`.

## Required interfaces
`axiom-protocol` as it is. Do not modify it.

## Implementation requirements
Public API (names are binding; add private helpers freely):

```rust
pub struct ServerInfo { pub name: String, pub version: String }

pub struct Router { /* … */ }
impl Router {
    pub fn new() -> Self;
    /// Registers a handler for method M. Panics if M::NAME is already registered
    /// or is "initialize"/"shutdown" (those are built in).
    pub fn method<M, F, Fut>(&mut self, handler: F) -> &mut Self
    where M: axiom_protocol::Method,
          F: Fn(M::Params, RequestCtx) -> Fut + Send + Sync + 'static,
          Fut: Future<Output = Result<M::Result, RpcError>> + Send + 'static;
    /// Called once when `shutdown` is received or the peer disconnects,
    /// before the shutdown response is sent.
    pub fn on_shutdown<F, Fut>(&mut self, hook: F) -> &mut Self
    where F: Fn() -> Fut + Send + Sync + 'static, Fut: Future<Output = ()> + Send + 'static;
    pub fn method_names(&self) -> Vec<String>; // registered + "initialize" + "shutdown", sorted
}

#[derive(Clone)]
pub struct RequestCtx { pub cancel: CancellationToken, pub notifier: Notifier, /* … */ }
impl RequestCtx {
    /// Registers a future that the router spawns only AFTER this request's
    /// response has been placed on the outgoing queue (and only if the
    /// handler returned Ok). Because the queue is FIFO, any notification the
    /// future sends is written after the response. May be called more than
    /// once; futures are spawned in registration order. This is how
    /// `task/start` guarantees "response before the first task/output".
    pub fn after_response<Fut>(&self, fut: Fut) where Fut: Future<Output = ()> + Send + 'static;
}

#[derive(Clone)]
pub struct Notifier { /* … */ }
impl Notifier {
    /// Queues a notification. Awaits when the outgoing queue (capacity 1024
    /// messages) is full: this is the backpressure path for task output.
    /// Returns Err(Closed) once the connection is gone.
    pub async fn notify<N: axiom_protocol::Notification>(&self, params: N::Params) -> Result<(), Closed>;
}

/// Serves one connection until `shutdown` completes or the reader hits EOF.
pub async fn serve<R, W>(reader: R, writer: W, router: Arc<Router>, info: ServerInfo) -> Result<(), ServeError>
where R: AsyncRead + Unpin + Send + 'static, W: AsyncWrite + Unpin + Send + 'static;

/// Typed client over the same framing.
pub struct Client { /* … */ }
impl Client {
    pub fn new<R, W>(reader: R, writer: W) -> Self;            // spawns its own read loop
    pub async fn request<M: Method>(&self, params: M::Params) -> Result<M::Result, RpcError>;
    pub async fn request_raw(&self, method: &str, params: serde_json::Value) -> Result<serde_json::Value, RpcError>;
    pub fn request_with_id<M: Method>(&self, params: M::Params) -> (RequestId, impl Future<Output = Result<M::Result, RpcError>>);
    pub async fn notify<N: Notification>(&self, params: N::Params);
    pub async fn send_line(&self, raw: &str);                   // for malformed-input tests
    /// Stream of server notifications as (method, params).
    pub fn notifications(&self) -> tokio::sync::broadcast::Receiver<(String, serde_json::Value)>;
}
```

Behaviour (each line is a test case; see `ipc.md` for the normative text):
1. Codec: one JSON document per `\n`; accept `\r\n`; ignore empty lines;
   lines over 64 MiB close the connection with `ServeError::LineTooLong`.
2. A line that is not valid JSON, or not a valid `Message` → response
   `{id: null, error: parse_error | invalid_request}`; the connection stays up.
3. Before a successful `initialize`: any other request → `not_initialized`;
   notifications are dropped.
4. `initialize`: built in. MAJOR mismatch → `unsupported` with details
   `{"supported": PROTOCOL_VERSION}`. Otherwise result with negotiated
   version, `info`, `method_names()`, and `HostInfo` computed from
   `std::env::consts` (`os`: linux/macos/windows; `path_separator` from
   `std::path::MAIN_SEPARATOR`). A second `initialize` → `invalid_request`.
5. Unknown method → `method_not_found`. Params that fail to deserialize →
   `invalid_params` with details `{"reason": "<serde error>"}`. Missing
   `params` is treated as `{}`.
6. Each request runs in its own Tokio task; a slow handler does not delay
   other requests. Responses are written as each handler finishes.
7. `$/cancel {id}`: if the request's response has already been queued,
   ignore. Otherwise cancel its `CancellationToken`, give the handler up to
   100 ms to return (so it can clean up), abort it if it has not, and send a
   `cancelled` error **regardless of what the handler returned**. This is
   the single race rule: "completed first" in `ipc.md` means "response
   queued before the `$/cancel` was processed". Unknown ids are ignored.
8. A handler panic is caught (`JoinError::is_panic`) → `internal` response;
   the connection stays up; the panic message goes to `tracing::error!`.
9. `shutdown`: run the hook, respond `{}`, flush, return `Ok(())`. EOF on the
   reader: cancel all in-flight requests, run the hook, return `Ok(())`.
10. `after_response` futures run only after the response was queued, and are
    dropped unrun if the handler returned `Err` or was cancelled.
11. All writes go through one writer task fed by a bounded channel
    (capacity 1024); a message is written and flushed whole (no interleaving).

## Constraints
- Dependencies allowed: `axiom-protocol`, `tokio` (features: rt, sync, io-util,
  macros, time), `tokio-util` (for `CancellationToken`), `serde`,
  `serde_json`, `thiserror`, `tracing`, `futures-util`. Dev: `tokio` full.
- No domain knowledge: nothing about workspaces, files or tasks.
- No `unsafe` (the workspace lint `unsafe_code = "deny"` applies).

## Acceptance criteria
- `crates/rpc` exists, is a workspace member, and exposes the API above.
- Every numbered behaviour has at least one test in `crates/rpc/tests/`
  using `tokio::io::duplex` to connect `serve` and `Client` in-process.
- A concurrency test proves (6): a handler sleeping 200 ms does not delay a
  fast request sent after it (fast response arrives first, total < 150 ms).
- An ordering test proves (10): a handler that registers an
  `after_response` future sending a notification always yields
  response-then-notification on the wire (run it 200 times).
- A backpressure test proves `Notifier::notify` suspends when the peer does
  not read and resumes when it does.
