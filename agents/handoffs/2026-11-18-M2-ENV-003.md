## The exact plan the user sees (Rust 1.84.0, Linux x86_64)
`<root>` = `<data dir>/toolchains/rust/1.84.0`.
1. **download** `https://static.rust-lang.org/rustup/dist/x86_64-unknown-linux-gnu/rustup-init`
   (21,347,088 bytes). The SHA-256 comes from `…/rustup-init.sha256`.
2. **extract**, format `file`: placed at `<root>/rustup-init`, made executable.
3. **run** `<root>/rustup-init -y --no-modify-path --default-toolchain none --profile minimal`,
   with `RUSTUP_HOME=<root>/rustup` and `CARGO_HOME=<root>/cargo`.
4. **run** `<root>/cargo/bin/rustup toolchain install 1.84.0 --profile minimal`, with the same
   variables plus `RUSTUP_TOOLCHAIN=1.84.0`.
5. **verify** cargo.
6. **verify** rustc.

Effects: network, writeManaged, runPrograms. `downloadBytes` is the rustup-init size. The
toolchain's own downloads are made by rustup and are not in the total.

## Deviations and decisions
- **"rustup missing" means missing from the managed root.** Each Rust version root gets its own
  rustup, about 20 MB.
  - A rustup on the user's `PATH` is not used: `rustup toolchain install` alone creates no
    proxies in the root, so `cargo`/`rustc` would have no stable location there, and it would
    tie the managed install to whatever rustup the user has.
  - Generic delegates without a bootstrap method still use `PATH`.
- **Four optional manifest fields** were needed for this; a manifest cannot express a
  bootstrap otherwise. They are additive: every existing manifest parses unchanged, and
  `drafts.rs` passes unchanged.
- **The bootstrap URL is the unversioned `rustup/dist/…` one, with its published checksum.**
  It always fetches the current rustup-init. The archive's `versions` (`["latest"]`) is never
  offered: methods with `provides` are skipped for versions and default selection.
- **The toolchain's own downloads are not in `downloadBytes`.** rustup makes them, and they are
  verified by rustup, not by us. The plan dialog (UI-002) should say so.
- **Outside the declared scope:**
  - `crates/protocol`: the additive manifest fields, as noted.
  - `schemas/` and `protocol.gen.ts`: regenerated.
  - `crates/axiomd`: the uninstall handler passes the manifest.
  - `.github/workflows/ci.yml`: the CI install step.
