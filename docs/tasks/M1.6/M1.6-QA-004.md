# M1.6-QA-004: Performance regression run against the M1.6 budgets

## Objective
The full bench, including the six M1.6 scenarios, is run on the redesigned shell
under the same conditions as the QA-002 baseline. Every budget P1–P12 of
`docs/design/performance.md` §3 and every existing budget row is reported as met or
not met, with numbers, in `docs/roadmap/verification/M1.6.md` §Performance.

## Context
`docs/design/performance.md` (all sections); the QA-002 baseline JSON in
`apps/desktop-tauri/bench/results/`; `motion-system.md` §5 (looping policy) and §7
(how motion is verified). Prototype indications: `docs/design/concepts.md` §4.

## Required interfaces
- `bench/run.sh --runs 3 --heavy-runs 3` with the QA-002 scenarios.
- The e2e-only probe (`src/e2e-probe.ts`).

## Implementation requirements
1. Run on the reference Linux machine (the one QA-002 used; quote `uptime`; load
   < 1.0), from a release build of the M1.6 head.
2. Run the full bench three times and keep all JSON files in `bench/results/`.
3. Produce a table: metric, baseline median, M1.6 median, delta, budget, verdict
   (✅/❌), for the ten existing rows and P1–P12. P8/P9 (idle with a task running,
   focused and unfocused) use the `idle-running` scenario. P12 uses
   `typing-under-stream`.
4. For any ❌: re-run that scenario three more times to exclude noise; if it stays
   ❌, profile it (WebKit inspector timeline, or `perf` on `WebKitWebProcess`),
   name the cause (component, CSS property, animation), and file a defect on the
   owning task with the evidence. Do not change product code here.
5. Additionally measure, with motion `off`, P7/P8 to show the motion setting's
   effect, and record it.
6. Record the bundle sizes (JS excluding Monaco, CSS, fonts) vs QA-002.

## Constraints
- Same machine, same load conditions and same engine version as the baseline;
  state any difference.
- No budget is changed in this task. Changing a budget needs the owner's written
  acceptance in the verification record (performance.md §3).

## Non-goals
- macOS/Windows measurements (QA-005); fixing regressions (owning tasks).

## Acceptance criteria
1. Every existing row and P1–P12 has a measured value and a verdict.
2. All rows are ✅, or each ❌ has a defect with profile evidence and either a fix
   re-measured here or an owner waiver quoted in the record.
3. The JSON files are committed and named in the record.

## Tests
- `apps/desktop-tauri/bench/run.sh --runs 3 --heavy-runs 3` (×3).
- `scripts/check.sh` green on the measured commit.

## Visual verification
None.

## Performance
This task **is** the performance verification: P1–P12 and the ten
`docs/migration/qt-to-tauri/performance.md` §2 rows.

## Failure conditions
- Comparing against numbers from a different machine or load.
- Reporting a single run when the spread exceeds 15% of the median.
- Marking tested with an unexplained ❌.

## Documentation updates
`docs/roadmap/verification/M1.6.md` §Performance; `docs/design/performance.md`
(a "Measured at M1.6 exit" column).

## Handoff
The verdict table, the JSON file names, the load average, and the defects filed.
