# 0021 An agent's own server, the proxy, and the browser
**Decision** (D-6, as recommended). What an agent runs may listen on this computer's loopback address, and the agent, its browser and its person may reach what it listens on; nothing else on this computer. Every such connection goes through the host, which checks that the port is listened on by a process of that agent's own tree, and nothing else does it. Commands still have no other network (K43).
**Listening.** The sandbox lets an agent's commands bind and accept on `127.0.0.1` and `::1`, and connect nowhere: not to the Internet, not to loopback (other people's servers, a database, a daemon's API would be reachable there). On macOS that is Seatbelt's `network-bind` and `network-inbound` on the local address only. On Linux the agent's commands are in a network namespace of their own already: they listen on its loopback, and reach their own servers there, because nothing else is in it; the host reaches it by entering that namespace from one thread of `axiom-spawn` for one connection, which the sandbox's owner may. On Windows commands are refused anyway (K4).
**Whose port.** The host asks the system which process listens (macOS `proc_pidfdinfo`, Linux `/proc/<pid>/net/tcp` and the descriptors of the tree), and only a process the agent's tree holds counts (`axiom-spawn` knows every tree). Not by trying ports. A port that has changed hands between the look and the connection is the remaining risk; the look is repeated on each new connection.
**The proxy.** One piece of the host (`host/src/proxy.rs`) through which an agent's browser and the person's views reach its servers, and through which, later, fetching and commands reach the Internet by the same policy (SI-13). It listens nowhere (SI-20): the browser's requests come to it over the DevTools pipe, not over a port, and a person's view is pictures over the wire.
**The browser** (W-50 to W-52) is a Chromium the person has installed (Chrome, Chromium, Edge, Brave), found as programs are; Axiom installs none. It runs in the host's control, in a process of its own, with a profile folder of Axiom's own for each session that is never the person's, headless, spoken to over `--remote-debugging-pipe` (no port), with every request paused and decided by the proxy (`Fetch.requestPaused`): an agent's own server is let through; another address is refused unless its person allowed that host as a fetch is allowed (K43); `file:`, `chrome:` and other schemes are refused; downloads are refused. What a page says is the agent's input, labelled as from the page (SI-17); its pictures reach the client as pictures only (SI-14). One holds the page at a time, the agent or its person, and that is shown; the agent's tools wait while its person holds it.
**Alternatives.** A proxy that listens on a loopback port with a token: SI-20, and any process of the user could use it. Allowing loopback outright: reaches whatever else listens there. The person's own browser with an extension: their profile, their logins, their history (T29, T45).
**Risk.** On macOS what an agent serves is on this computer's own loopback: any program of its person's can reach it there, not only the host. What it serves is not opened in the person's own browser, whose profile and logins an agent's page would reach (T29, T45); their view of it is Axiom's browser. Chromium is large and its sandbox is its own; it runs as the person, outside Axiom's sandbox, with only the profile folder of its own and every request decided by the host. WebSockets and WebRTC do not pass through `Fetch`: WebRTC is turned off by switch, WebSockets are let through only to an agent's own server, refused by host rules for everything else (`--host-resolver-rules`).
**Revisit.** When the proxy carries commands' traffic to the Internet, and when Windows has a sandbox (K4).
