# M1.6-DESIGN-001: Record the approved visual direction and owner decisions (ADR-0013)

## Objective
The owner's choice of visual direction and their answers to decisions D1–D10
(`docs/design/concepts.md` §6) are recorded in an accepted ADR. The design documents
are marked approved, or re-derived for the chosen direction, and every M1.6 task file
matches those decisions. No M1.6 implementation task may start before this one is
Tested.

## Context
This is an **architect/owner task** (governance §Change requests: an architect
session). Phase A produced three concepts plus a recommended synthesis, with
prototypes in `experiments/e5-visual-concepts/` and screenshots in
`docs/design/concepts/`. Read, in order: `docs/design/creative-brief.md`,
`docs/design/concepts.md` (§3 evaluation, §5 recommendation, §6 decisions), then
`design-system.md`, `motion-system.md` and `workspace-spec.md` only as far as the
decisions touch them.

## Required interfaces
- `docs/decisions/README.md` (ADR numbering and format); ADR-0011 (licences),
  ADR-0012 (Tauri shell).
- `docs/architecture/governance.md` rule 9 (no placeholder UI), rule 1 (dependencies).
- Task files `docs/tasks/M1.6/*.md` (front matter is parsed by `scripts/tasks.py`).

## Implementation requirements
1. Obtain the owner's answer to each of D1–D10 **in writing**: the chat message or
   issue comment is quoted with its date in the ADR. An agent may not infer an
   answer. If one is missing, the task stays In Progress.
2. Write `docs/decisions/ADR-0013-visual-identity.md` (status Accepted) containing:
   the chosen direction (D1) and the screenshots that define it; the **material
   grammar** (raised = pressable, recessed = holds a value or accepts input,
   flat = content and structure); the palette approach (generated themes from
   `themes.json`, fixed semantic state slots, accent never decorative); the
   **motion policy** (transform/opacity only, one layout commit per toggle,
   stepped loops ≤ 8 updates/s, at most 3 visible loops, paused when unfocused,
   Standard/Reduced/Off); the **scope rule** (no M2–M7 surface in production
   before its milestone); and the answers to D2–D10 with their consequences.
3. If D1 = the recommended synthesis: change the status line of each file in
   `docs/design/*.md` from "proposal" to "approved by ADR-0013 (date)". If D1 names
   A, B, C or another combination: rewrite `design-system.md` §2 (tokens), §5 (type)
   and §9 (components), `motion-system.md` §2 (tokens) and the affected
   `workspace-spec.md` sections from that concept's prototype CSS
   (`experiments/e5-visual-concepts/src/concepts/{a,b,c}.css`), and record what
   changed in the ADR.
4. Amend the task files whose decision changed: D2 rejected → SYSTEM-002 becomes
   "record fallback stacks only"; D3 changed → SHELL-003 and SURFACES-003
   requirements; D4 changed → SHELL-002 (rail); D5 rejected → INTERACTION-001 and
   SURFACES-002 drop the setting; D6 rejected → SHELL-006 keeps red stderr; D7
   rejected → INTERACTION-004 set to `blocked` with note "cancelled by ADR-0013" and
   removed from QA-006's `depends_on`; D8 rejected → SYSTEM-004 uses `title` only;
   D9 changed → add the flag task; D10 changed → SURFACES-003.
5. If D2 is approved, file `docs/decisions/proposed/CR-M1.6-DESIGN-001-ofl-fonts.md`
   proposing that ADR-0011 allow OFL-1.1 font assets (not code), with the licence
   text location and redistribution conditions; the architect resolves it in the
   same session by an ADR-0011 status note or a new ADR.
6. Update `docs/roadmap/current.md`: M1.6 approved, the next task is QA-001/QA-002/
   SYSTEM-001/SHELL-001 (parallel), and the decisions in one table.

## Constraints
- No production code (`apps/`, `crates/`, `editor/`) changes in this task.
- The ADR is immutable once accepted (governance §ADRs): later changes need a new
  ADR.
- Frozen contracts (IPC 0.1, editor bridge 1) are not touched; if a decision
  requires a contract change, stop and file a CR.

## Non-goals
- Implementing any token or component.
- Re-running the prototypes' measurements (QA-002 measures the real app).
- Choosing values the owner did not decide; open details stay in the specs.

## Acceptance criteria
1. ADR-0013 exists, is Accepted, quotes the owner's answers to D1–D10 with dates,
   and states the material grammar, motion policy and scope rule.
2. Every `docs/design/*.md` status line names ADR-0013, or the file was re-derived
   for the chosen concept.
3. Every M1.6 task file is consistent with the decisions (a reviewer can check
   each of D2–D10 against the named tasks in requirement 4).
4. `docs/roadmap/current.md` names M1.6 as approved and lists the next tasks.
5. `scripts/tasks.py check` passes; `scripts/tasks.py next` shows the four
   unblocked tasks.

## Tests
- `python3 scripts/tasks.py check` — no errors.
- `python3 scripts/tasks.py` — DESIGN-001 tested; QA-001, QA-002, SYSTEM-001 and
  SHELL-001 Ready.
- `scripts/check.sh` — green (documentation only, but the board check runs).

## Visual verification
None produced. The ADR links the approved reference screenshots
(`docs/design/concepts/r-*.png`, or the chosen concept's), which become the
references for every later "compare against" step.

## Performance
None. The ADR copies budgets P1–P12 from `docs/design/performance.md` §3 by
reference, unless the owner changes one (record it).

## Failure conditions
- Any of D1–D10 is answered by inference instead of by the owner.
- A design document claims "approved" while still describing a rejected option.
- A task file still requires work that a decision cancelled.

## Documentation updates
`docs/decisions/ADR-0013-visual-identity.md` (new), `docs/decisions/README.md`
(index), `docs/design/*.md` (status lines or re-derivation), `docs/tasks/M1.6/*.md`
(amendments), `docs/roadmap/current.md`; the CR from requirement 5 if D2 is
approved.

## Handoff
A table D1–D10 → owner answer → date → files amended. List any open detail the
owner deferred and the task that will settle it.
