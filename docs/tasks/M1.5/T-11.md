# T-11: Editor isolation spike: Monaco behind a narrower capability

## Objective
Measure whether Monaco in an iframe or secondary webview with a narrower
capability is worth its cost against the in-document editor, and record the
decision. The spike lives on a spike branch and is not merged to `main` as
product code.

## Context
Source: implementation-roadmap.md §1 (wave D), §2 (T-11, decision rule). Trade-off:
`docs/migration/qt-to-tauri/architecture.md` §2.6 (security model deltas: the
whole UI is the page today) and §3.3 (one webview vs. a separate editor
webview). Measurement method: `docs/migration/qt-to-tauri/performance.md` §1.

## Required interfaces
- `apps/desktop-tauri/` (spike branch, `task/T-11`).
- Bridge-1 message set (frozen) as the only editor interface.
- `apps/desktop-tauri/bench/` measurement harness (read; extend only on spike branch).

## Implementation requirements
1. Work only on branch `task/T-11`. The spike branch may change `apps/desktop-tauri/`.
2. Implement an isolated editor surface: Monaco in an `<iframe>` or a secondary
   webview with a capability narrower than the main window's (no `daemon_request`).
   The bridge-1 messages are passed through the host or `postMessage`; the set is
   unchanged.
3. Measure, on the same machine and workload as performance.md: (a) additional
   memory (PSS) of the isolated editor over the in-document editor; (b) p95 typing
   latency in ms over at least 500 keystrokes.
4. Decision rule (roadmap T-11): adopt isolation if it costs ≤ 40 MiB PSS **and**
   ≤ 5 ms p95 typing latency over the in-document editor; otherwise record why not.
   The rule is stated before measuring and is not changed after.
5. Record the result in `docs/migration/qt-to-tauri/` as a new section of
   `architecture.md` §3.3 or a new file `editor-isolation.md` in that directory
   (one of the two; state which).
6. Record the security effect: which commands the isolated page can reach
   (must be none beyond the bridge-1 path).

## Constraints
- No merge of the spike to `main`; the handoff names the branch and commit.
- Frozen contracts unchanged (IPC 0.1, editor bridge 1); no new message.
- Scope note: `apps/desktop-tauri/` is named as a whole for the spike branch only;
  any part of it outside the spike is not edited.
- Do not open windows on a developer desktop; use `headless.sh` on Linux.

## Acceptance criteria
1. Branch `task/T-11` exists with the spike; `main` is unchanged by this task (req. 1).
2. The isolated surface has no `daemon_request` capability (req. 2, 6).
3. Measurements for PSS and p95 latency are recorded with method and machine (req. 3).
4. The decision (adopt / not adopt) follows the pre-stated rule (req. 4).
5. The result is recorded in the named document (req. 5).

## Tests
- On the spike branch: `cd apps/desktop-tauri && pnpm test` and `pnpm run check`.
- Latency: `apps/desktop-tauri/bench/run.sh --scenario <typing>` (the scenario
  that exists in the harness; if none exists for typing, the handoff says so and
  the measurement is not run).
- Capability check: the test that parses `capabilities/*.json` (T-03) run on the spike.

## Failure conditions
- The spike is merged to `main` as product code.
- The decision rule is changed after the measurement.
- Typing latency or PSS is estimated rather than measured.
- The isolated surface gains any command beyond the bridge-1 path.

## Documentation updates
- `docs/migration/qt-to-tauri/architecture.md` §3.3 or `editor-isolation.md` (new), as in req. 5.
- `docs/roadmap/current.md` (governance rule 10).

## Handoff
The spike branch name and commit, the PSS and p95 numbers with the rule outcome,
and the owner's decision request (adopt, or record "not adopt" with reason).
