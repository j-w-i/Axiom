## Critical

### 1. A session becomes permanently unreadable once a page passes 8 MiB
Status: fixed

- Where: server.rs:314 (`PAGE = 500` events in one message), session.rs:143-149 (join gap of up to 1024 events in one message), outbox.rs:40 (any size accepted when empty), server.rs:378 (`session.list`).
- The host emits lines longer than its own `MAX_LINE`; the client rejects them and reconnects with the same `after` forever.
- Confirmed four ways, the first three giving "a line exceeds 8388608 bytes":
  - 12 finished items of 1 MiB, on the recent path and again on the history path after a restart.
  - A single item of 1.5 MiB of NUL. JSON escaping is ×6 and `ITEM_LIMIT` is 4 MiB, so one event can be 24 MiB. A `cat` of a binary is enough, and splitting pages does not fix it.
  - Two sessions with 5 MiB `workspace` strings: `session.list` fails for everyone, permanently.
  - Args nested 124 deep: accepted and stored, but the Rust client fails with "recursion limit exceeded" because wrapping adds nesting depth.
- Fix: page by encoded bytes (about 256 KiB) in `read` and in the join gap. Bound item text, args, result, title and workspace by encoded size before journalling. Cap JSON depth. Paginate `session.list`. Make the outbox refuse any single line over `MAX_LINE`.

### 2. Any same-uid process, with no token, can end the host
Status: fixed

- server.rs:139 `let s = s?` returns from `serve` on any `accept()` error.
- Confirmed with `ulimit -n 256` (the macOS launchd soft default on this machine): one client plus raw connections gave "Too many open files" and the host exited with code 1. The run was still open in the journal, so the shutdown path was skipped. There is no connection cap.
- The Windows accept thread has the same flaw: `while let Ok(..) = sock.accept()` stops on any error (static only).
- Fix: log and back off on accept errors, cap unauthenticated and total connections, raise RLIMIT_NOFILE.

### 3. Unauthenticated memory and fd leak, and memory amplification
Status: fixed

- server.rs:204-236 allows an 8 MiB pre-hello line, and the parse error echoes the attacker's string.
- server.rs:303 times out on the `JoinHandle` without aborting the writer. Dropping the handle detaches the task, which keeps the fd and buffer forever.
- Confirmed: 40 connections, each sending an 8 MiB method name and never reading. 12 s later (hello limit 5 s) there were 45 unix fds against 4 before, 365 MB RSS, and `status.clients` = 1, so the leak is invisible.
- Confirmed: 8 unauthenticated connections sending `"params":[0,0,…]` peaked at **2.1 GB** RSS, not returned afterwards.
- Confirmed for authenticated half-closed clients: 20 sockets still held after 6 s, RSS 24 → 157 MB.
- Fix: 4 KiB line limit before hello, no echo of input in errors, `writer.abort()` after the timeout, cap concurrent unauthenticated peers.

### 4. One damaged row stops the whole application from starting
Status: fixed

- journal/lib.rs:203-206 and 230-268: `recover()` decodes every event of every session and `?`s out.
- Confirmed: one event body set to `{` in one of two sessions gave `axiom-host: journal: EOF while parsing…`, exit 1, with no way into the other session.
- If it happens while live, server.rs:326 swallows the error and sends `Resync{0}`. Every re-follow gets it again (3/3). The Dart client re-follows immediately with no backoff, so that is a hot loop (by reading the code).
- Fix: quarantine per session, log, return a typed error on follow, never resync-0 on a read error.

## High

### 5. Ending an item scans the whole session; `event_delta` is never used
Status: fixed (query plan tested; timing not repeated)

- journal/lib.rs:73 and 154. EXPLAIN shows `SEARCH event USING PRIMARY KEY (session=?)`.
- Confirmed per ended item: 45 µs at 600 events, 1.3 ms at 21k, 2.6 ms at 42k, **6.5 ms at 104k**, linear. It runs on the one journal thread, so it stalls every session. That breaks "commit p99 ≤ 1 ms" and passes decision 0004's 5 ms revisit trigger.
- Fix: `delete from event indexed by event_delta where …`. Verified: about 0.11 ms flat at 104k. Adding `is not null`, a non-partial index, or swapping the columns did not help.

### 6. A 5 s write lock or transient I/O error kills sessions until restart, silently
Status: fixed

- session.rs:254-263 (`broken` is permanent), store.rs:115-120 (one failed commit fails every session in the group).
- Confirmed with an external `begin immediate` held 6.5 s: both streaming sessions went broken. Afterwards `session.list` said `running:true` while `status.runs` = 0, and the status carried no error. The comment at session.rs:256 says "`host.status` says why"; it does not.
- A new `replay.start` on the broken session is **accepted** and a follow succeeds, yet nothing is ever recorded or sent.
- Fix: retry BUSY/IOERR, or reopen the actor from the journal on next use. Answer say/follow/start with an error, and expose it in status and list.

### 7. Group commit: an SQLite auto-rollback mid-group breaks atomicity
Status: fixed (tests)

- journal/lib.rs:119-136 and 143. After SQLITE_FULL (also IOERR/NOMEM) SQLite drops the outer transaction. The next `savepoint()` then opens its own transaction and its RELEASE commits.
- Confirmed with `max_page_count`, appending a, b(too big), c: the batch returned `Err("cannot commit - no transaction is active")` and the store would tell all three they failed, but **c is committed** (last_seq 2) while a is gone. c's actor then lags its own journal, so a follow gets history, an `after` beyond the actor's seq, resync 0, and loops (inferred).
- Fix: check `db.is_autocommit()` after each append and abort the batch, rolling back and retrying members one by one.

### 8. Two follows on one connection reorder and repeat
Status: fixed

- server.rs:262-272 aborts the old task but never sends `Cmd::Unfollow`, and a `Cmd::Follow` already queued survives the abort. The existing registration keeps pushing live events between history pages.
- Confirmed: live follower at seq about 20k, re-follow from 0. The stream went …20054, 1… with 7 backward jumps and 7 duplicates. wire.md §4 says "in order, nothing twice".
- Fix: send Unfollow before spawning; give follows a generation; in the actor skip if `joined.is_closed()`.

### 9. Answers are unbounded
Status: fixed

- outbox.rs:54 `force` is used for every answer. AGENTS.md and lib.rs:5 say every queue is bounded.
- Confirmed: 946 KB of `session.list` requests, nothing read, gave 634 MB RSS.
- Fix: stop reading requests while the outbox is over its limit.

### 10. Shutdown loses endings and accepts new work
Status: fixed; with the journal locked by another program at the stop, endings may be unwritten (K29)

- server.rs:152-163.
- Runs behind backpressure (scripts of `ask`, each an Intent at about 4 ms): with 2–3 sessions the 2 s limit passed and **10 of 12 run endings were not journalled**. 300 slow runs were fine.
- `replay.start` after an accepted `host.shutdown` is answered `accepted` and left `running` in the journal.
- SIGTERM has no handler although the tokio `signal` feature is enabled: the run was left open and the token file left behind. Logout and reboot take this path.
- Fix: a closing flag checked by `handle`; a JoinSet of runs awaited before syncing instead of a 50 ms sleep; handle SIGTERM, SIGINT and SIGHUP.

### 11. `recover()` and `quick_check` read everything at every start
Status: fixed

- journal/lib.rs:78 and 230-294. `open_runs` exists but is not used.
- Confirmed with everything already ended: 841 MB journal, 430 ms; 140 MB with 500k small events, 247 ms. The budget is p99 ≤ 50 ms; the published 12/25 ms was measured on empty directories. A 500 MB session gave 511 MB RSS at startup, because pages are 2000 events with no byte bound.
- Fix: recover only sessions with `open_runs > 0` or an open marker, page by bytes, run quick_check only after an unclean exit or in the background.

### 12. Durability claims
Status: fixed

- overview.md "Machine loses power: the last ≤ 33 ms of deltas may be lost" is false. Stream commits are WAL+NORMAL, so everything since the last Intent commit or checkpoint can go, including `item.ended`, `run.ended`, titles and tool results.
- `session.create` is answered without a sync: measured 35–94 µs against 4.2 ms for an Intent commit. journal/lib.rs:37 promises Intent "for what a person did".
- `intent()` (session.rs:268) omits `ItemStarted{Tool}`, `ItemStarted{Prompt}` and `SessionTitled`. A tool call's intent event is not durable.
- Sound here: FULL plus `fullfsync` does take effect per batch (4.1–4.3 ms against 0.02–0.03 ms, stable when alternating).

### 13. History reads run on the commit thread with no byte bound
Status: fixed

- store.rs:86.
- Confirmed: following a session of 500 × 1 MiB items paused another session's stream for 309 ms and peaked at 1.7 GB RSS.
- Fix: a separate read-only connection (WAL allows it) plus byte-bounded pages.

## Medium

### 14. Terminal escapes reach the terminal (SI-15)
Status: fixed

- cli/main.rs:29 and 58.
- Confirmed: `axiom replay S evil.jsonl` prints raw `ESC ]0;pwned BEL ESC[31m` to stderr via the serde error text. `axiom sessions` prints raw U+009B (C1 CSI), DEL and U+202E.
- `plain()` (line 101) passes newlines and bidi overrides into approval lines: an `ask` subject containing `\n-- Completed` prints a forged run-ended line.
- Fix: escape all output including errors, and all Cc/Cf/Zl/Zp. Show approvals on one line.

### 15. `axiom follow` drops the tail of every live item
Status: fixed

- session.rs:195 discards pending text at End and cli/main.rs:73 prints no text if any delta was shown.
- Confirmed: 60 words streamed, it printed w0–w55.
- Fix: flush pending deltas before End, or print the remainder of `text`.

### 16. Recovery leaves the agent `running`
Status: fixed

- journal/lib.rs:249-257 writes no `agent.state`. Confirmed after kill -9: the last `agent.state` is Running. `app/lib/host/session_model.dart` ignores `RunEnded`, so the UI shows it running forever (by reading the code).
- It also loses the "[N more bytes were not kept]" count.

### 17. Memory that is never released
Status: fixed; resident memory still grows with macOS malloc's cache

- The `sessions` map is never evicted, and each actor keeps 1024 events with no byte bound (up to 4 MiB each).
- Confirmed: four finished 60 MB sessions that nobody follows gave 142 → 194 → 225 → 270 MB RSS.

### 18. Deltas are overtaken by ends of other items
Status: fixed

- session.rs:191-199: End does not drain, against the doc line at 168.
- Confirmed: text of item p said before the end of t is journalled after it (seq 8 against 7).

### 19. A repeated local name in a script orphans ids
Status: fixed (not re-run in full)

- replay.rs:83 and 103. Confirmed: the first item `p` and the first request `q` are never closed although the run ends `completed`. recover() later adds `item.ended` after `run.ended` (inferred).

### 20. `run.cancel` ignores `session`
Status: fixed for cancel (K16 for the rest)

- server.rs:412. Confirmed: cancelling under an unrelated session id succeeds.

### 21. The endpoint depends on the client's TMPDIR
Status: fixed

- net.rs:54 and 136 call `paths.endpoint()` instead of reading `run/endpoint`.
- Confirmed on 9053730: with a long data dir and a different TMPDIR, the CLI gets ENOENT. The Dart client reads the file; the Rust one does not.
- On Linux without TMPDIR the directory is `/tmp/axiom-<FNV of a public path>`, which anyone can pre-create (DoS; static). macOS tmp cleaning can remove a live socket while the lock is held (unconfirmed).
- The short directory is never removed. There are 115 `axiom-<hex>` dirs in this machine's TMPDIR, some from test runs including the reviewer's.

### 22. Two hosts on one journal
Status: fixed

- The lock is in `run/`. Confirmed: after `rm -rf run`, a second host reported "ready" on the same journal.
- Fix: lock a file beside the journal or the journal itself, e.g. `locking_mode=EXCLUSIVE`.

### 23. File modes
Status: fixed

- Confirmed: `journal.db`, `-wal` and `run/lock` are 0644. The threat model B8 says 0600. `private_dir` creates with the umask and then chmods; use `DirBuilder::mode(0o700)`. Owner uid is never compared. The expected peer uid is the directory's owner, not geteuid.

### 24. Windows (static)
Status: partly (K7)

- Two OS threads per unauthenticated connection, uncapped. A "socket out" thread blocked in `write_all` is never released.

## Checked and found sound
- The single-follow join: history → gap → live, with folded holes and an uncommitted actor seq.
- Seq continuity and savepoint isolation for ordinary failures.
- Nothing sent before its commit.
- The hello deadline is absolute, so slow drip does not extend it.
- The Outbox has no lost wakeups and the actor never waits on a client.
- Lock held until after socket removal; the socket's umask window is covered by the 0700 directory; token file creation; token compare.
- The idle-exit `notified()` race (worst case, a client is dropped and must respawn).
- Cancel delivery through the dropped watch sender.
- Newer-schema refusal; kill -9 recovery of shown text; stranger and garbage handling.
