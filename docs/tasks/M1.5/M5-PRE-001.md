# M5-PRE-001: Preview-engine spike: CDP inspection without Qt WebEngine

## Objective
Answer architecture.md §4.1 with a recorded experiment: can a preview of a
running UI be rendered into the app while being inspected over the Chrome
DevTools Protocol (CDP), either (a) by an external Chromium driven over CDP and
rendered into the app by screenshot or stream, or (b) by WebView2's CDP on
Windows only? The result, with a recommendation, is recorded in
`experiments/README.md`.

This is an **experiment, not product code**. Nothing in `apps/` or `crates/`
changes. Nothing in the product may depend on `experiments/` (see
`experiments/README.md`).

## Context
Source: implementation-roadmap.md §1 (M5-pre, wave A, parallel) and
`docs/migration/qt-to-tauri/architecture.md` §4.1 (open question: M5 preview
engine). ADR-0001 rejected system webviews partly because M5 needs "one known
Chromium with CDP"; ADR-0008 (`docs/decisions/ADR-0008-visual-inspection.md`)
defines the inspection model. The Qt-era reference result is E1/E3 in
`experiments/README.md`. Read `experiments/README.md` for the recording format
and the environment block.

## Required interfaces
- Experiment directory `experiments/e4-preview-cdp/` (new).
- `experiments/README.md` — new section `## E4 — …` (the only existing file
  edited).
- Reads only: `docs/decisions/ADR-0008-visual-inspection.md`,
  `docs/protocols/inspection.md`.

## Implementation requirements
1. Create `experiments/e4-preview-cdp/` containing a README (method and how to
   rerun), the spike code (any language already used in `experiments/`), and
   `results.json`.
2. Option (a): launch a Chromium (the one already installed on the machine, or
   a headless shell downloaded for the experiment, recorded with version) with
   `--remote-debugging-port` on a loopback address; connect over CDP; load a
   fixture page; capture a frame with `Page.captureScreenshot`; measure time from
   navigation to the first frame and the per-frame latency for 60 frames.
3. Option (b): only if a Windows machine is available; otherwise record
   "not run: no Windows host" in the result. Do not estimate it.
4. Measure, for each option run: Chromium version, OS, time to first frame,
   p95 frame-capture latency, resident memory of the browser process group.
5. Use a temporary data directory; never the user's browser profile
   (`--user-data-dir` to a temp directory).
6. Test that the DOM element → source mapping remains reachable through CDP
   (`DOM.getBoxModel` or `Runtime.evaluate` on a stamped element) — or record
   that it is not.
7. Record in `experiments/README.md` §E4: hypothesis, setup, observed table,
   the recommendation (one of: adopt option a / adopt option b / reject both),
   and the open risks (licensing of the bundled browser, Linux display stack).
8. Pass/fail criterion stated before running: recommend adoption only if
   first frame < 1 s and p95 capture latency < 100 ms on the measured machine,
   and CDP element lookup works. Report the numbers even if the criterion fails.

## Constraints
- No change under `apps/`, `crates/`, `scripts/`, `schemas/`, `.github/`,
  `docs/` other than `experiments/README.md`.
- No dependency added to the workspace `Cargo.toml` (`experiments` is excluded
  from the workspace).
- Do not open a window on a developer's desktop: run headless, or under the
  private Xvfb from `apps/desktop-tauri/scripts/headless.sh` on Linux.
- Do not print to any daemon stdout channel (not applicable; keep in mind).

## Acceptance criteria
1. `experiments/e4-preview-cdp/` exists with README, code and `results.json`
   (req. 1).
2. `experiments/README.md` has a §E4 entry with the hypothesis, observed table
   and recommendation (req. 7).
3. The recommendation is one of the three allowed values and follows from the
   pre-stated criterion (req. 8).
4. Reviewer `git status` (read-only) shows no change under `apps/` or `crates/`
   (the central requirement of this task).
5. Option (b) is either measured on Windows or explicitly "not run" with reason.

## Tests
- `cd experiments/e4-preview-cdp && <command in its README>` — reproduces
  `results.json` within stated variance.
- `cargo test --workspace` is unaffected (run `scripts/check.sh rust` once to
  show no drift).

## Failure conditions
- Any file under `apps/` or `crates/` is modified.
- The experiment uses the user's browser profile or a visible desktop window.
- Numbers are reported without the machine, OS and Chromium version.
- The recommendation contradicts the pre-stated criterion without explanation.
- Results are estimated rather than measured.
