## Behaviour implemented
- `SettingsStore` (`settings`): typed properties `theme`, `editorFontSize`, `editorFontFamily`, `editorWordWrap`, `reopenLast`, `loaded`; setters call `settings/set`; **properties change only when the daemon's `settings/didChange` (or the initial `settings/get`) arrives**, never optimistically. A rejected value (e.g. `invalid_params`, details `{key}`) leaves the property unchanged, emits `errorOccurred("That value is not valid for <key>.")` and re-emits every NOTIFY so bound controls snap back to the real value. Reloads automatically whenever the daemon becomes Ready (so a restarted backend is re-read).
- `Theme.dark` now follows `settings.theme` (`dark`, or `system` + OS scheme dark); the temporary `Qt.styleHints` binding from SHELL-001 is gone from `Main.qml` (the OS scheme is only an input to `system`).
- Whenever a setting, `Theme.dark` or the mono family changes, and after the editor's `ready`, the editor receives `configure` with resolved values (empty family → `Theme.monoFamily`).
- `SettingsDialog.qml` (File ▸ Settings…, Ctrl+,): Appearance (Theme System/Light/Dark), Editor (font size spin 8–40, font family field with the resolved default as placeholder, Word wrap), Workspace (Reopen last folder at startup). Changes apply immediately; the only button is Close. Every control has a visible label and an accessible name; controls are bound to the store (value reasserted after each user action).
- Help ▸ About: app version, backend (`axiomd <version>` or "not connected"), protocol `0.1`, Qt version, and the data directory as passed with `--data-dir` or "default location" (no daemon method reports it in protocol 0.1; none added).
- New design-system controls used by the dialog: `AxCheckBox`, `AxSpinBox`, `AxTextField`.
- Also fixed: the Explorer header floated to the middle of the side bar while no folder was open (caught in the settings screenshots).

## Race found in my own test (worth knowing)
The daemon handles requests concurrently (ipc.md), so two `settings/set` calls issued back-to-back can be applied in either order; the test that set `light` then `dark` without waiting failed 5 times in 12. The test now waits for the daemon's confirmation of each value. Application code is not affected (the store follows whatever the daemon last reports), but a UI that sends two conflicting writes without waiting could end on the older one. The dialog sends one write per user action.

- The temporary OS-follow binding was removed from `Main.qml`, but `Theme.qml` still initialises `dark` from `Qt.styleHints.colorScheme` before the shell sets it (first frame only).
