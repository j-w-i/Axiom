## Behaviour implemented
- `notify` 8 (`RecommendedWatcher`, recursive); one watcher per workspace shared through a `Weak<WatchShared>`; the first `watch()` starts it (plus one OS thread doing debounce), dropping the last handle drops the watcher, which ends the thread.
- Paths → `WorkspacePath` (strip root, `/` separators); events outside the root and the root itself are dropped.
- Filter: any path with a `.git` component, or under a directory the ignore rules mark ignored (uses `IgnoreCache::classify` on the parent, which already propagates ancestors), is dropped. Ignored files and ignored directory entries themselves are reported.
- Debounce 100 ms from the first *reported* event of a batch; merge rules per path (created+modified→created, X+removed→removed, removed+created→modified); sorted by path. Renames: From→removed, To→created, Both→removed+created, unknown side → checks the disk.
- `need_rescan` or a watcher error → batch of exactly `{path: "", kind: modified}`. Each subscriber has a 64-batch buffer; if it is full, the batch is not blocked on, and the subscriber's next batch is replaced by the same re-list marker, so loss is signalled rather than silent.
- Changes to `.gitignore`/`.ignore`/`.git/info/exclude` invalidate the matcher cache (the same code path as writes through the crate) before filtering.

## Platform caveats (from notify docs, not observed here)
- macOS FSEvents coalesces and delays events, may report renames with unknown sides and merged flags (the code handles unknown rename sides by checking the disk); events can arrive for paths created just before `watch()` started.
- Windows (ReadDirectoryChangesW): buffer overflow → rescan flag (handled as overflow); rename events usually come as From/To pairs; deleting the watched root stops the watcher.
- Linux: inotify watch limit (`fs.inotify.max_user_watches`) can make `watch()` fail with an I/O error; it surfaces as `WsError::Io`.

## Deviations and decisions
- Created+modified+removed within one batch ends as `removed` even if the file never existed before the batch (spec rule "anything + removed → removed").
- An atomic write (temp + rename) may surface as `created` or `modified`; the temp file normally merges away (created+removed → removed) and is reported as `removed` at worst.
- The thread is a plain OS thread (std mpsc) because `notify`'s callback is synchronous; no tokio runtime is required to call `watch()`.

## Known defects / limitations
- Temp files from atomic writes may appear as a `removed` path (`.axiom-tmp-*`) in batches; harmless to clients but noisy. A later task may filter the prefix.
